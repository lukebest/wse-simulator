1. 总结

Flat butterfly n=2 (pipelined) 在二维 Mesh 上实现 radix-2 的 flattened butterfly 集合通信：每条逻辑 leg 为单跳直连（Manhattan XY 路由，不经过中点 PE）， stride 取 1, 2, 4, … < dim；X/Y 两维按算子类型分阶段（broadcast/reduce-scatter 与 gather 方向相反）。

Pipelined 指按 flit 建立依赖：某一 flit 在 PE 上完成上一跳接收后的下一 cycle 即可进入下一跳， 不必等同 block 内全部 flit 到齐。调度在多种 flat-bf 实现（链式、dim-wise、周期级 router 模拟）间取最小 makespan。

设计要点
  • 功能正确性优先：broadcast 采用 root 行链 + 列扩散；reduce/gather 在 router 路径上要求跨轴上游聚合完成后再发下一跳。
  • 与树/环对齐的下界：4×4、1 flit 时 broadcast/reduce 均为 6 cycle，与最远角点 (3,3)→(0,0) 的 6 跳一致。
  • Router：无全局 stride/轴屏障；assignButterflyColors 将 flow 划分为边不相交的 VC（color），再配合每 cycle 边互斥与跨轴聚合就绪（见 §7）。

2. 拓扑：2D Mesh 上的 n=2 Flattened Butterfly

2.1 物理网络

每个 PE 位于坐标 (x, y)，0 ≤ x < cols，0 ≤ y < rows。 相邻 PE 通过东/西/南/北四条有向物理边互连（实现中为 XY 最短路径多跳 path(a,b)）。

3. 流水模型与指标

3.1 Flow 与 Flit

  • Flow：一条逻辑通信 from → to，携带 flits 个 flit、payload 描述（root block / partial sum / k block(s)）。
  • 路径：path(a,b) 为 Mesh 上 XY 逐跳边序列；每 hop 占用 1 cycle。
  • 周期：period 为同 flow 内相邻 flit 启动间隔；pipelined 实现多为 1。

3.2 Makespan（延迟）

无 hopCycles 时： makespan = max_f ( start_f + (flits_f−1)×period_f + |path_f| )。 Router 调度后为每个 flit 记录每跳出发 cycle hopCycles[i][h]，取全局最大末跳出发 +1。

3.3 Max edge sharing

同一 cycle、同一有向物理边上并发 flit 数的峰值；理想无冲突时为 1。着色与每 cycle 边互斥用于压低该指标。

5. 各集合通信算子方案

5.1 Broadcast — 复制语义

目标：root (0,0) 的数据块复制到每个 PE。

Flat 链式（当前默认之一）：

  1. 行阶段：仅在 y=0 上 (0,0)→(1,0)→…→(cols−1,0)，start = x，形成行内流水。
  2. 列阶段：对每个 x，(x,0)→(x,1)→…，start = x+y。
  3. 经 finishBroadcastSchedule 解析边冲突并 enforceBroadcastDependencies，保证子节点在父节点 flit 到达后才转发。

5.2 Reduce — 归约到 root

目标：每个 PE 一份 partial，最终在 (0,0) 得到全局和（仿真中用标量累加验证）。

Flat 链式（与 2D tree reduce 同构的时空 stagger）：

  1. 每列自下而上：(x, rows−1)→…→(x,0)，start = rows−1−y。
  2. 每行自右向左：(cols−1,0)→…→(0,0)，start = (rows−1)+(cols−1−x)。

4×4、1 flit 时最远点 (3,3) 关键路径 6 跳 / 6 cycle，与 Manhattan 下界一致。

5.3 Gather — 搬运到 root

目标：root 持有全部 rows×cols 个数据块。

  • 列链：自 (x, rows−1) 向上聚合，发送 base × (rows−y) flit（块数随深度增加）。
  • 行链：自 (cols−1, 0) 向左，发送 base × rows × (cols−x) flit。
  • 所有列链 start=0 并行启动，再经 resolveEdgeConflicts 错开冲突边。

5.4 Allgather — 每 PE 持有全集

目标：每个 PE 最终持有 N 份块（环式复制语义）。

  • Dim-wise exchange：按 stride 成对双向交换，held 块数每轮翻倍（调度期抽象）。
  • Flat 环式：cols−1 轮行环 + rows−1 轮列环，每轮每 PE 向邻居复制一块（不掏空源）。

5.5 Allreduce — 全局归约再扩散

  • Dim-wise exchange：与 butterfly allreduce 拓扑相同，双向 partial 相加，无单独 broadcast 阶段。
  • 拼接：scheduleFlatBfReduce + scheduleFlatBfBroadcast，时间轴串接。

5.6 Butterfly 拓扑流集合（Router 输入）

butterflyFlows 按算子生成全部 stride leg：

  • butterflyBcastFlows — 全行 X + 全列 Y 向前
  • butterflyGatherReduceFlows — Y 反向再 X 反向
  • butterflyExchangeFlows — 双向 exchange

每条 flow 标记 axis、stride，供 router 就绪判断与着色使用。

6. Router 硬件设计方案

软件中的 scheduleButterflyRouter 对应一种可在每个 PE 上实例化的 分布式 Mesh Router：不依赖全局 stage 屏障，在单 cycle 内完成 “就绪检测 → 仲裁 → 单跳发射”。

6.1 模块划分（每 PE 一份）

Ingress / 聚合缓冲
  • 每 flit 槽位记录到达时间 avail[flit]
  • Broadcast：仅 root 注入 avail[i]=i
  • Reduce/Gather：本地 partial 在 cycle 0 可注入
就绪逻辑 canDepart
  • 查所有以本 PE 为终点的上游聚合 flow（reduce/gather 含跨轴）
  • 要求对应 flit 已完成且到达时间 ≤ 当前 cycle
  • 若无上游，则查本地 avail[flit]
Flow 状态 RAM
  • 每 (flow_id, flit)：hop_index、各跳 depart_cycle[]
  • 与软件 progress Map 同构
发射仲裁
  • 同 PE、同 cycle：按 colorId 分队列
  • 同 color 内按 stride 序（reduce/gather 大 stride 优先）
  • 每条物理出边每 cycle 最多 1 个 flit（edgeBusy）

6.2 边着色（概要）

Color 由 assignButterflyColors 对 butterfly flow 集合做边冲突图着色得到； 用于 Router 同 PE 多 flow 就绪时的仲裁顺序，并与「每 color 边不相交」的静态路由子图对应。 完整定义、各算子分色规律与硬件映射见 第 7 节。

实现注意
  • Reduce 若在 router 中仅等待同轴上游，会错误并行 X/Y，使 makespan 低于 Manhattan 下界（如 4 cycle）；已改为 reduce/gather 等待任意轴指向本节点的上游聚合完成。
  • 修依赖后 4×4 router reduce makespan 升至 8 cycle，pickMin 改选 6 cycle 的 flat 链式。
  • Broadcast 禁止非 root 行在列扩散前参与行向发送；与 tree 一致。

6.5 建议 RTL / 微架构参数

  • 颜色队列深度：≥ 图着色数（4×4 reduce 约 4～8 色，随 mesh 增大）。
  • Flow 上下文：存 flow_id, flit_id, hop, axis, stride, out_dir。
  • 就绪比较器：对每个 active flow 查询上游 flow 完成位（可用 per-flow 完成向量或链路 credit）。
  • 输出：每物理出端口 valid/ready 与 flit 数据；与 Mesh NIU 对接。

7. Color 机制与各 color 静态路由

在仿真器里，color（colorId）不是「目的地址查表」意义上的单条静态路径， 而是对 butterfly flow 集合 做物理边资源划分后得到的 虚拟通道（VC）类号：同一 color 内的任意两条 flow 在 Mesh 上不共用同一条有向物理边（边 ID 为 x,y->x',y'）。 Router 运行时再用 color 作为仲裁优先级（color 编号小者优先），并与全局 edgeBusy（每 cycle 每边至多 1 flit）配合。

7.1 何时着色、着色对象

场景调用位置flow 来源
Butterfly RouterscheduleButterflyRouterbutterflyFlows 生成的全部 stride leg（broadcast / reduce / allreduce 等）
Flat gather 链scheduleFlatBfGather 末尾列链 + 行链（stride 恒为 1）；4×4 上通常仅使用 color 0
Flat 链式 broadcast/reduce不着色用固定 start stagger 或 finishBroadcastSchedule，无 colorId

7.2 分配算法 assignButterflyColors

  1. 对每条 flow f，展开其 XY 路径 f.path 上的所有物理边。
  2. 若两条 flow 共享任一边，则在冲突图中连边。
  3. 按 flow 下标顺序（BF0, BF1, …）做贪心着色：取不与已着色邻居冲突的最小非负整数作为 colorId。
  4. 返回 colorCount = max(colorId) + 1（至少为 1；若全部落在 0 上仍可能报告 2，见 7.5 注）。
静态不变式（per color）

对固定 colorId = c，集合 { f | f.colorId = c } 中任意两条 flow 的边集交集为空。 因此可在硬件上把该 color 视为一张边不相交的子图：其中所有 leg 在「拓扑占用」意义上可并行，不会争抢同一条有向链路标识。

7.3 运行时：color 在 Router 里做什么

在 scheduleButterflyRouter 的每个 cycle、每个 PE (x,y)：

  1. 收集所有就绪的 (flow, flit, hop)，按 colorId 分桶。
  2. 按 colorId 升序遍历桶；桶内再按 departSortKey 排序（reduce/gather：大 stride 优先）。
  3. 对候选 hop 检查 edgeBusy：该 cycle 该物理边若已被占用则跳过（与 color 无关，全色共享边互斥）。

因此：color 解决的是「同 PE 多 flow 同时就绪」时的先后次序；edgeBusy 解决的是「同 cycle 同边」的互斥。 二者叠加后得到周期精确的 hopCycles 与 makespan。

7.4 各 color 对应的「静态路由方案」

每条 butterfly flow 的几何路由在创建时已固定：from → to，Mesh 上走 XY 最短路径（每 stride leg 为 1 跳或 2 跳）。 colorId 是在多条 flow 并行时，把「可能争用同一边」的 flow 分到不同 VC 的编号。 下表描述 4×4、base=1 时典型分色规律（由当前 BF* 顺序与贪心着色导出；mesh 变大时 stride 越大往往需更多 color）。

Broadcast（butterflyBcastFlows，4×4 共 2 色）

colorId包含的 stride / 轴静态路由含义示例 leg（每行 y 类似）
0 stride=1，X 与 Y 相邻单跳扩散网：root 行/列上 (x,y)→(x+1,y) 或 (x,y)→(x,y+1) (0,0)→(1,0)，(0,0)→(0,1)，…
1 stride=2，X 与 Y 跨两格单 leg（flattened butterfly 长边）：(x,y)→(x+2,y) 或 (x,y)→(x,y+2) (0,0)→(2,0)，(0,0)→(0,2)，…

stride=2 的 8 条 X leg 与 8 条 Y leg 因共享中间边，在 4×4 上被拆成 color 0 与 1 各一半（由贪心顺序决定具体 BF 编号归属）。

Reduce（butterflyGatherReduceFlows，4×4 共 2 色）

colorId包含的 stride / 轴静态路由含义示例 leg
0 stride=2，Y 与 X 粗粒度聚合：先「两格一跳」向 row 0 / col 0 收拢（如 (x,2)→(x,0)，(2,0)→(0,0)） BF0–BF3（列底→行 0），BF12–BF15（行右半→左）
1 stride=1；以及部分 stride=2 细粒度 / 高行：最后一行向上 (x,3)→(x,1) 等，与 color 0 边集不交的 stride-1 补全 BF4–BF7，BF8–BF11，BF16–BF23

Reduce 的逻辑阶段仍是 Y 再大 stride → X 再大 stride；color 只保证边不冲突，不改变 stride 语义。Router 上须配合 跨轴上游就绪（见 6.4），否则会出现 makespan 低于曼哈顿距离的错误并行。

Allreduce（butterflyExchangeFlows，4×4 共 3 色）

colorIdstride静态路由含义划分规则（4×4）
0 1 所有相邻 PE 对双向 exchange（X/Y 各 16 条 flow） 整网 stride-1 配对
1 2 stride-2 交换中 x 为偶数起点 的 leg：0↔2（每行） 0,0↔2,0，2,0↔0,0，…
2 2 stride-2 交换中 x 为奇数起点 的 leg：1↔3 1,0↔3,0，3,0↔1,0，…

Y 向 stride-2 同样按「偶/奇 tile」落入 color 1 与 2。可视为两张并行的 stride-2 交换平面 + 一张 stride-1 平面。

Gather 链（4×4，colorCount=2 但仅用 color 0）

15 条链式 flow 路径边互不相同，贪心着色全部落在 color 0；无第二条边不相交子图。 静态上即「单 VC 上的列向 + 行向聚合树」，与 tree gather 拓扑一致，仅通过 resolveEdgeConflicts 错开 start。

7.6 硬件：把 color 实现成静态 VC 路由

  • 配置期：集合通信下发时，为每条 leg 写入 (from, to, stride, axis, colorId)；等价于把该 flow 绑定到某条边不相交子图 / VC。
  • 数据面：flit 带 colorId（或 VC index）；XY 路由仍由 from,to 决定，不是「color → 下一跳端口」查表。
  • 仲裁：每 PE 每 cycle，按 VC 编号从小到大服务就绪队列；同 VC 内大 stride 优先（与 departSortKey 一致）。
  • 边仲裁：出边级 edgeBusy 与 VC 正交——即使不同 color，同一 cycle 仍不能占用同一边（与仿真一致）。
  • 着色资源：综合工具可据 assignButterflyColors 预计算 colorCount，作为 VC 深度下界；mesh 越大、stride 越多，VC 数上界越高。
与「静态路由表」的对比
传统 NoC 路由表
VC × dest → next_hop，每跳查表。
Flat-bf color
VC × flow_id → 整条 leg 的 (from,to) 与 hop 序列；每跳方向由当前坐标与目标 XY 决定，VC 只解决多 flow 边资源划分与仲裁次序。

8. 与 Basic 模式对比

scheduleButterflyBasic 使用 finishFlattenedStages：按 stride 分 stage，stage 内并行，stage 间串行。 Pipelined 在 stage 内也可流水，且 router 路径可跨 stage 重叠发射（在依赖满足时）。
